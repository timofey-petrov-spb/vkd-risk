## 1. Что это и для кого

Сервис для аналитика ГОГУ (главной оперативной группы управления) при
подготовке выхода в открытый космос. Аналитик задаёт начало и длительность
ВКД и период поиска начала, а сервис получает орбиту МКС и открытые данные
о космической погоде, считает условия вдоль траектории по каждому механизму
воздействия отдельно (космическая погода на траектории и статистика природных
метеороидов), сравнивает два-три окна одинаковой длительности и выдаёт
рекомендацию либо явный отказ с видимым правилом, охватом и списком
недостающих данных. Это исследовательский прототип поддержки решений: допуск
к реальной ВКД остаётся за уполномоченными специалистами, и сервис его не
выдаёт.

Развёрнутое решение: **https://vkd-risk.streamlit.app/** (Streamlit
Community Cloud, точка входа `streamlit_app.py`, ветка `main`; обновляется
автоматически при пуше).

**Проверено живым 19.09.2026 в 08:00 UTC:** `GET /healthz` — 200
`{"status":"ok"}` за 0,54 с, `GET /` — 200 за 1,84 с. Чего эта проверка не
доказывает: экран Streamlit рисуется по websocket, и код ответа HTTP о нём
ничего не говорит — проверка экрана глазами остаётся отдельным пунктом
(`docs/design/CHECKLIST_PREDEFENCE.md`). Площадка разворачивает ветку `main`
удалённого репозитория: если локальный коммит туда не выложен, по ссылке
работает предыдущее состояние, и это надо сверять перед показом.

По ссылке выше ставить ничего не нужно. Локально сервис поднимает **одна
команда**:

```
python -m streamlit run app/main.py
```

Она печатает адрес в терминале (по умолчанию `http://localhost:8501`).
Один раз до неё — `python -m pip install -r requirements.txt`; проверки —
`python -m pytest -q`.

  загрузке страницы сервис пробует
  живые запросы (тайм-аут `[sources].timeout_s` = 6 с на адрес,
  слой `vkd.sources`, адреса — `config/settings.toml`):

  Kp `kp.gfz.de/app/json/` за последние двое суток, TLE — цепочка из трёх
  адресов по порядку (`celestrak.org/NORAD/elements/gp.php?CATNR=25544`,

  Удачный ответ записывается в `data/cache/<ключ>` вместе с временем получения.
  Сверх тайм-аута каждого адреса есть **общий предел на все живые источники одного
  рендера** — `[sources].total_deadline_s` = 12 с (`app/fetch_guard.py`). Он нужен
  потому, что зависание на разрешении имени (DNS) тайм-аутом `requests` не покрывается
  вовсе: `socket.getaddrinfo` ждёт столько, сколько ждёт системный резолвер, и на
  площадке с ограниченным исходящим доступом первый рендер не наступал. По истечении
  предела попытка бросается, тот же кортеж собирается без сети (кеш → снимок
  репозитория → честное «данных нет»), а причина словами попадает в статус каждого
  запрашивавшегося источника, в снимок, на экран и в выгрузку. Замер на коммите
  слияния шестого круга: при зависании резолвера 60 с и 300 с первый рендер занял
  13,8 и 13,9 с — то есть предел плюс собственный рендер, и от длительности зависания
  не зависит (`docs/PROGRESS.md`, раздел 1б; `tests/test_deploy_fetch_guard.py`).
- Что грузит браузер зрителя (не сервер). Глобус вкладки «Карта» — единственное
  место, где страница обращается наружу мимо Python: библиотека three.js r128
  (`cdnjs.cloudflare.com`, 603 445 Б в разобранном виде, по сети 149 872 Б —
  ответ приходит сжатым `gzip`) и текстура Земли 4096×2048
  (`cdn.jsdelivr.net/npm/three-globe@2.42.4`, 1 461 877 Б = 1,39 МБ, JPEG, по сети
  столько же; запасная 2K — `threejs.org`, 512 606 Б). Замерено 19.09.2026
  запросом к этим адресам (`Content-Length` и длина разобранного тела).
  Версии в адресах закреплены, но самих файлов нет ни
  в `requirements.txt`, ни в репозитории: если адрес перестанет отвечать, глобус
  скажет об этом по-русски и отошлёт к плоской карте — ни одно число при этом
  не меняется. Сервер этих байтов не передаёт; после первого открытия ссылки они
  приходят из кеша браузера.
- Что работает без сети. При отказе источника берётся `data/cache/`. Снимок
  репозитория в цепочке ровно один — элементы орбиты: `data/orbit/iss.tle`
  (эпоха 18.09.2026 03:26Z, получен 18.09.2026 21:08Z) вместе с записью
  `data/orbit/manifest.json`, по которой сверяются байты, адрес и время
  получения (`_bundled_tle` в `vkd/sources/live_cache.py`). Для GOES и Kp
  снимка в цепочке НЕТ: `data/spaceweather/goes_protons_3day.json`
  (наблюдения по 17.09.2026 19:10Z) читает только демонстрационный
  `experiments/demo_pipeline.py`, а рабочий слой `vkd.sources` его не
  подставляет — проверено чтением кода 19.09. Поэтому без сети и без кеша
  GOES и Kp получают статус «данных нет», и это показывается, а не подменяется
  нулём; раньше здесь было написано, что снимок GOES подставляется, — неверно.
  Справочная копия `data/spaceweather/iss.tle` (эпоха 17.09.2026 11:56Z) тоже
  в цепочку не входит — у неё нет свидетельства получения.
  Статус источника при этом — строка слоя с давностью данных: «получено по
  сети», «проверенный кеш», «отказ сети: проверенный кеш» (так подписан и
  снимок репозитория: признак `cache_origin = bundled_verified_A3_receipt`
  остаётся в записи и в выгрузке), «данных нет», «источник исключён
  пользователем». Орбита текущего режима требует TLE
  не старше `tle_max_age_days` (3 сут) относительно обеих границ горизонта:
  устаревший снимок даёт «орбита недоступна», покрытие обязательной линии
  отсутствует, вердикт `insufficient`, заглушка не подставляется (Р-О2), —
  текущий режим без сети живёт только на свежем кеше. **Срок годности снимка
  считается, а не предполагается:** предел 3 сут применяется к дальней границе
  горизонта, поэтому при настройках по умолчанию (период поиска 12 ч +
  длительность 6 ч = 18 ч) снимок с эпохой 18.09 03:26Z перестаёт годиться
  20.09.2026 в 09:25 UTC, а при максимальных ползунках (24 ч + 8 ч = 32 ч) —
  19.09.2026 в 19:25 UTC. Обновить снимок перед показом:
  `python scripts/refresh_orbit_snapshot.py` (отчёт) и `--write` (запись).
  Скрипт ходит тем же слоем источников и по тем же адресам, что приложение,
  и пишет файл только если полученный набор СВЕЖЕЕ; иначе честно говорит, что
  обновлять нечего. Прогон 19.09.2026 09:5x UTC: CelesTrak с этой машины не
  отвечает (тайм-аут на обоих адресах), `api.wheretheiss.at` даёт эпоху

  репозитории. То есть свежее того, что закоммичено, через цепочку адресов
  сейчас не достать, и это ограничение, а не недосмотр.
  Там же видно и следствие порядка адресов: живой путь берёт ПЕРВЫЙ ответ без
  ошибки (`vkd/sources/live.py`, `tle_latest`), поэтому при молчащем CelesTrak

  давность), но при настройках по умолчанию такой набор перестаёт годиться уже

  сети не требуют: архив DONKI `data/archive_2024/` и реестр A1

## 3. Что делает сервис

Один экран, один путь пользователя (О5): запрос в боковой панели → полоса
состояния (режим, орбита с методом и статусом строгости, эпоха элементов
или дата создания OEM с давностью, в текущем режиме — последние GOES и Kp
с уровнем шкалы, в истории — отсечка и число записей, не использованных
после отсечки, признак сценария; каждое значение — плашка в полосе
состояния, отдельных баннеров на экране нет) → предупреждения о состоянии
источников одним блоком → ответ первым (панель вердикта с правилом,
причинами, охватом и устойчивостью) → карточки окон-кандидатов (состояние,
минуты в аномалии, флюенс, метеороиды, GOES или прогноз Kp, условия,
покрытие по механизмам) → в строгом режиме строка «Проверка после отсечки»
(что наблюдалось потом; в расчёт не входит) →
лента времени → вкладки «Объяснения», «Окна и факторы», «Методика», «Карта»,
«Наблюдения и прогнозы», «Данные» и на профессиональном уровне
«Устойчивость и нормы». «Методика» стоит третьей — сразу после чисел и до
карты: получил вердикт → увидел числа → проверил, откуда они взялись.
Интерфейс (`app/main.py`, разметка в `app/ui.py`) только рендерит снимок,
который собирает конвейер `app/compute.py` (`run()`); тот же конвейер строит выгрузку, примеры и повторы.

Три результата (CONTRACT, раздел 0):

1. Картина факторов по времени — одна лента (`app/viz.py`, `timeline`):
   слева 12 ч прошедших наблюдений, справа горизонт окон; линия «сейчас» /
   «отсечка» / «начало периода». Два ряда с общей осью времени, а третий
   появляется, только если события на горизонте есть (`make_subplots`,
   высоты 0,46 / 0,34 / 0,20, без событий — 0,58 / 0,42); пустой ряд не
   рисуется, вместо него под графиком стоит строка подписи. Первый ряд —
   «Экспозиция по окнам»: накопленные минуты в аномалии от начала каждого
   окна ступенями цветом окна, итог подписан числом на конце ступени;
   пролёты аномалии — закрашенные полосы, окна-кандидаты — светлые полосы,
   граница периода начала — штриховая линия. Окно без пролётов даёт ровный
   ноль, а не пустое место. Слева от «сейчас» экспозиции нет по определению
   (работ в прошлом нет): полоса прошлого затенена и подписана. Сырое |B|
   по IGRF на всей траектории (период поиска плюс длительность, шаг 1 мин)
   осталось отдельной линией, свёрнутой в легенде. Второй — Kp: в текущем режиме наблюдения GFZ столбцами и
   GOES ≥10 МэВ линией по правой оси за последние 12 ч; в строгой истории —
   прогноз Kp NOAA по 3-часовым интервалам из выпуска до отсечки; в разборе —
   наблюдения Kp окончательного ряда GFZ из архива (карточки DONKI —
   резерв); порог Kp 7. Цвет во втором ряду означает происхождение величины

   логарифмической осью с подписанными делениями шкалы S только тогда, когда
   достигает первого порога S1 (10 pfu); иначе оси нет, а максимум потока
   печатается строкой под графиком. Третий ряд — маркеры событий и прогнозов

2. Сравнение окон одинаковой длительности: карточки окон под вердиктом

3. Рекомендация либо явный отказ с правилом. Пять исходов

Три режима (боковая панель, «Режим»):

- «Текущая обстановка» — начало периода поиска равно текущему времени UTC,
  живые источники с кешем, автообновление.
- «Исторический разбор» — дата в пределах 1 мая — 30 июня 2024 и час начала;
  весь архив без отсечки; орбита — OEM NASA/JSC как реконструкция; в полосе
  состояния плашка «Архив: весь, без отсечки — разбор после факта».
- «Прогноз из прошлого» — та же дата, отсечка публикации равна началу
  периода; используются только записи с известным временем публикации не
  позже отсечки, прогнозы NOAA — из выпусков до отсечки; в полосе состояния
  плашка «После отсечки не использовано: N записей» (раздел 5, «Отсечка»),
  поимённый список — во вкладке «Данные». Под карточками окон —
  строка «Проверка после отсечки»: что наблюдалось потом по окончательному
  ряду Kp GFZ и уведомлениям, опубликованным позже отсечки; в расчёт это не
  входит и служит только сопоставлением прогноза с фактом.

Запрос: длительность ВКД 60–480 мин (шаг 30), период поиска начала
60–1440 мин (шаг 60), два или три окна со сдвигом начала внутри периода.
Границы запроса проверяются до расчёта: сдвиг окна ограничен текущим
периодом поиска (при сокращении периода сдвиг уменьшается и об этом
печатается строка), окна нумеруются по времени начала, одинаковые начала
дают предупреждение. Все времена UTC.

Два уровня интерфейса (переключатель «Уровень интерфейса»):

- «Оперативный» (по умолчанию) — полоса состояния, вердикт, карточки окон,
  лента, вкладки; во вкладке «Объяснения» окно выбирается переключателем
  (объяснения доступны для любого окна-кандидата, не только для первого), на
  этом уровне показываются условия и до четырёх основных величин выбранного
  окна; ссылки на первоисточник в карточках; кнопки выгрузки.
- «Профессиональный» — всё, включая пороги и настройки (порог аномалии,
  канал, свежесть GOES, триггер Kp, допустимый возраст TLE — поверх
  `config/settings.toml`), все карточки каждого окна с сырыми записями,
  вкладку «Устойчивость и нормы» (таблица сетки порогов с двумя исходами в
  каждой ячейке, допуск, панель норм),
  происхождение и ограничения орбитального модуля во вкладке «Данные».

«Что если» — стресс-сценарий (`vkd/windows/scenario.py`): задержка начала
работ 0–180 мин (сдвиг окон при прежней длительности — изменение плана, не
улучшение условий), моделируемое протонное событие с началом через заданное
число минут и уровнем 10/100/1000/10000 pfu, скачок Kp. Синтетические
входы помечены `is_simulated`, метка распространяется на весь результат и
выгрузку (в полосе состояния — плашка «Сценарий: моделируемые значения», в
тексте условий — слово «МОДЕЛИРУЕМОЕ»); у них нет времени публикации,
поэтому в строгий режим они не проходят и в кеш не попадают. Панель
сценария доступна во всех режимах.

Устойчивость (`vkd/windows/sensitivity.py`): оценка пересчитывается на сетке
порога аномалии (порог − 2000, порог, порог + 2000 нТл) и канала захваченных
протонов (12,5 / 30 / 50 МэВ). В каждой ячейке сетки правило применяется
дважды, и ячейка несёт **два исхода**: лучшее окно при нулевом допуске
(ранжирование) и предпочтительное окно с итоговым допуском равнозначности.
Допуск по минутам — разброс **разности** минут между двумя лучшими окнами
по оси порога (не меньше 1 мин): порог сдвигает оба окна синфазно, поэтому
разброс абсолютных минут одного окна допуском быть не может. Допуск по
флюенсу — разброс отношения флюенсов тех же окон по оси канала, не меньше
настройки ×1,5. Печатается «выбор устойчив» / «выбор меняется на сетке
порогов» — и отдельно, устойчиво ли ранжирование без допуска; если выбора
нет ни в одной ячейке, так и сказано («сетка исход не меняет»).

Надёжность: у источников GOES и Kp три состояния в боковой панели —
«включён», «отказ: только кеш» (живого запроса нет, кеш с давностью,
покрытие частичное и объявлено) и «исключён: нет данных» (обязательная
линия без покрытия → «оснований недостаточно», экран не падает); значение
попадает в `request.disabled` снимка. Статусы каждого источника —
«получено живьём с <адрес>», «отказ источника: кеш, давность N мин»,
«снимок репозитория», «отказ всех адресов TLE (…)», «источник исключён
пользователем — данных нет». В исторических режимах живые наблюдения не
запрашиваются, а проверка отказа делается отдельным флажком «Исключить Kp
из архива». Ошибка орбитального модуля (устаревший TLE,
непокрытый OEM) — статус «орбита недоступна», не заглушка. Ход шагов
показан индикаторами (источники; траектория, поле, оценка, устойчивость;
область аномалии на карте). Отсутствие данных выражается `None` и статусом
покрытия, никогда нулём; частичное покрытие объявляется в причинах и не
блокирует рекомендацию.

## 4. Два механизма и охват

Обязательный охват — дословно `CONTRACT.md`, раздел 2:

| линия | статус | что даёт |
|---|---|---|
| космическая погода на траектории | **обязательна** | наблюдение GOES и Kp; внешние прогнозы NOAA и DONKI; наш расчёт условий вдоль траектории |
| статистический поток MMOD | **обязательна** | ожидаемое число попаданий по одной обоснованной модели |
| сближения SOCRATES | **отдельная линия, не обязательна** | внешний прогноз сближений станции; её отсутствие не блокирует рекомендацию, а входит в заявление об охвате |

Буря, протонное событие и радионарушение — разные явления, не складывать.
Три времени каждого сообщения ведутся раздельно: событие, срок действия,
публикация.

Что реализовано в коде:

- Механизм 1 «космическая погода на траектории» (`mechanism_id =
  spaceweather`, обязательный): минуты в аномалии, флюенс захваченных
  протонов по прил. А ОСТ 134-1044-2007, минуты доступности протонов
  ≥10 и ≥100 МэВ по вертикальной жёсткости обрезания A3 (CONTRACT, раздел 3;
  в сохранённых примерах обе величины равны нулю — по дипольному обрезанию
  в спокойных условиях эти протоны на трассе окна недоступны, и это сказано
  в ограничении величины), поток протонов GOES ≥10 МэВ; в
  исторических режимах ещё три внешних прогноза NOAA из выпусков до
  отсечки (максимум прогноза Kp в окне, суточные вероятности S1+ и
  протонного события); условия проверки по GOES, Kp, датированным
  событиям DONKI (протонные события, бури с Kp ≥ 7, опубликованный прогноз
  прихода выброса с ожидаемым Kp ≥ 7) и прогнозу Kp NOAA.
- Механизм 2 «статистика метеороидов» (`mechanism_id = mmod_stat`,
  обязательный, `vkd/assess/meteoroids.py`): ожидаемое число попаданий
  природных метеороидов массой не менее 10⁻³ г на одностороннюю случайно
  кувыркающуюся пластину 1 м² за окно по ECSS-E-ST-10-04C Rev.1 —
  поток Grün (формула 10-1) × множители Table J-6 по фактической высоте
  каждой точки трассы, интеграл по времени × площадь
  (`meteoroid_hits_track`, спецификация А `docs/methods/METEOROIDS_GRUN_SPEC.md`).
  Трасса покрывает меньше 95 % окна → покрытие частичное. Второй величиной
  механизма идёт «активных метеорных потоков на дату (календарь IMO)» — это
  **признак активности, а не поток**: вклад потоков даты в число попаданий не
  рассчитан (ECSS 10.2.2.2c требует их учёта для миссий короче трёх недель),
  ZHR календаря — визуальная величина, не поток на пластину. Техногенный
  мусор не включён. И то и другое объявляется в правиле величины и в
  недостающем охвате. Вне диапазонов Table J-5 (масса) и Table J-6 (высота
  100…100 000 км) — отказ «вне области применимости ECSS», не кламп.
- Линия 3 «сближения SOCRATES» (`mechanism_id = conjunctions`,
  необязательная): тип `Conjunction` и подсчёт записей с TCA в окне
  реализованы; конвейер передаёт пустой список, в охвате печатается
  «сближения SOCRATES — нет данных».

Заключение всегда относится к объявленному охвату: под вердиктом и в
`report.md` печатается «Охват: учтено — космическая погода на траектории,
природные метеороиды ECSS/Grün; не учтено — сближения SOCRATES — нет
данных, вклад метеорных потоков даты в число попаданий — не рассчитан
(календарь даёт только признак активности), техногенный мусор статистически —
не включён» (`vkd/windows/compare.py`, `coverage_declared`,
`coverage_missing`).

## 5. Методы кратко

Траектория (`vkd/orbit`, область А, A3; подключена мостом
`vkd/integration/orbit_bridge.py`, заглушки орбиты нет). Текущий режим:
TLE NORAD 25544 от слоя источников кладётся в
`data/cache/orbit_root/<sha12>/` с манифестом (SHA-256, время получения,
адрес) и копиями коэффициентов IGRF, модуль А проверяет байты снимка по
хешам; SGP4/WGS72 (`sgp4`, `skyfield`), геодезические координаты WGS84
(в метаданных `method = sgp4`, `frame = TEME -> ITRS / WGS84`,
`source_id = celestrak_gp`). Обе границы горизонта не дальше
`tle_max_age_days` (3 сут) от эпохи TLE — инженерный предел, не оценка
ошибки; иначе «орбита недоступна» (Р-О2). Исторические режимы: NASA/JSC
OEM из реестра A1 (26 файлов, покрытие 29 апреля — 13 июля 2024),
кусочная кубическая интерполяция Эрмита, EME2000 → ITRS/WGS84
(`method = oem_interp`, `source_id = nasa_jsc_oem`). Строгий отбор OEM по
доказанной публикации до отсечки не проходит (публичная доступность
версии в 2024 году не доказана), поэтому берётся OEM, созданный и
изменённый в S3 не позднее отсечки, как ОБЪЯВЛЕННАЯ реконструкция
(`strictness = declared_reconstruction`, `is_reconstruction = true`,
ограничение в происхождении и на экране; Р-О1 — решение Б, ждёт
подтверждения А). Шаг 1 мин, начало и конец включены: число точек =
период поиска + длительность + 1, до 1921 (32 ч; CONTRACT, раздел 0 и 12
«Горизонт»). Показываются источник, эпоха элементов (в истории — дата
создания OEM), давность в часах, метод и статус. Отчёт происхождения А
(`trajectory_with_provenance`: записи с SHA-256, сегменты, ограничения)
входит в снимок (`trajectory_meta.provenance`) и в выгрузку
(`raw/orbit_provenance.json`). В текущем режиме текст TLE сохраняется в
снимке для повтора; в истории повтор от TLE не зависит.

Поле и магнитные координаты. |B| в каждой точке — полная модель IGRF до
степени 13 на момент точки (A3, `ppigrf` с коэффициентами
`data/orbit/IGRF13.shc` для 2024 года и `IGRF14.shc` для текущих дат,
хеши в `data/orbit/manifest.json`; в метаданных `field_model = IGRF-13`
или `IGRF-14`; вне таблицы коэффициентов — отказ без экстраполяции). A3
отдаёт также L, B/B_0 и вертикальную жёсткость обрезания Стёрмера
центрального наклонённого диполя (статус `approximation`), но для входа в
таблицы ОСТ конвейер их не использует: центральный диполь в ядре аномалии
даёт L ≈ 1,07 — ниже первой оболочки таблицы (1,14), а вне ядра B/B_0
уходит за точку отражения, и флюенс на всей трассе получался тождественно
нулевым. Вместо этого `vkd/assess/magcoords.py` (R11) считает L и B_0 от
центра эксцентричного диполя: ось из g_10, g_11, h_11, смещение центра по
квадрупольным членам того же IGRF (Fraser-Smith 1987) на дату средней
точки трассы. Модуль смещения в сохранённых примерах: 603 км (0,0946 R_E)
в шести примерах на май–июнь 2024 и 609 км (0,0956 R_E) в трёх примерах
текущего режима на сентябрь 2026 — смещение считается на момент расчёта,
поэтому по годам оно разное; направление — в сторону
западной части Тихого океана; L = r' / cos²λ'_m, B_0 = B_eq / L³, B — полное IGRF точки от A3.
Каждая точка несёт `mag_method = dipole`, `mag_status = approximation`; в
карточке величины печатается «дипольная L — исследовательское
приближение»; сводка (смещение, число точек, число помеченных) — в

бы интеграл спектра E⁻² более чем на 20 %) от E_min до последнего узла

величины. Поток прил. А — всенаправленный; интеграл по времени считается
трапециями по фактическим dt, единица «част./см²». При неполном охвате
показывается только известный вклад, полный флюенс неизвестен. Канал E_min:

доля времени окна с известными концами интервалов; экстраполяции нет.

сохраняется в `numerical_integration.json`; это не граница физической ошибки.

Метеороиды (`vkd/assess/meteoroids.py`, реализация Б по спецификации А
`docs/methods/METEOROIDS_GRUN_SPEC.md`, версия `grun-ecss-2020-v1`). Поток
Grün на 1 а.е. F_met,0(m) = 3,15576·10⁷·(F_1 + F_2 + F_3) (формула 10-1
ECSS-E-ST-10-04C Rev.1, с. 76–77; воспроизводит Table J-5 стандарта на
30 массах 10⁻¹²…10² г с точностью 0,6 %); поправки низкой орбиты
F = F_0·G·s_f·K по Annex C, формула (C-25), множители Table J-6 линейно по
высоте (на 400 км G = 2,00, s_f = 0,63, K = 1,09). По окну
(`meteoroid_hits_track`): F по фактической высоте каждой точки трассы,
интеграл трапециями по фактическим интервалам dt, начало и конец окна
включены, N = A·∫F dt / 31 557 600 с; число точек само по себе не
добавляет минуты экспозиции. Контрольное число: 400 км, 1 м², 6 ч,
m ≥ 10⁻³ г → N = 5,609728·10⁻⁷, совпадает с контрольными данными А
(`data/meteoroids/grun_reference.json`) с относительной точностью 10⁻¹⁰.
Модель изотропна и от наклонения не зависит; неопределённость потока по
стандарту ×0,33…3 (J.2.3.2) хранится в объекте результата.

Условия — политика прототипа (`vkd/windows/compare.py`, `Thresholds`;
значения — `config/settings.toml`, раздел 14). GOES ≥10 МэВ ≥ 1000 pfu
(S3 и выше) — приоритетное предупреждение: окно требует срочной проверки
специалистом. 10–1000 pfu (S1–S2) — предупреждение о протонном событии,
окно исключается из автоматического выбора. Kp ≥ 7 (G3, `kp_check`) —
триггер дополнительной проверки; тот же порог применяется к наблюдению
Kp, уведомлению DONKI о буре, опубликованному уведомлению о приходе
выброса и прогнозу NOAA.
Датированные события (в том числе моделируемые), чей интервал действия
или физический интервал пересекает окно, дают условие только четырёх
видов (R10): протонное событие SEP — карточка или уведомление
(«приоритетное», если в записи есть слово «приоритет»); геомагнитная буря
GST — только если в теле уведомления (реестр A1) назван Kp ≥ 7, уровень
не назван → условие с пометкой (консервативно), Kp ниже порога →
информация в картине; прогноз прихода выброса к Земле (`CME_ARRIVAL`) —
только из ОПУБЛИКОВАННОГО уведомления DONKI с собственным временем выпуска:
время прихода и объявленный в теле диапазон максимума Kp («expected range of
the maximum Kp index is 8-9»), порог сравнивается с границей диапазона по
настройке `[history].cme_kp_range_bound` = `max` (верхняя, консервативно;
показатели обеих границ опубликованы рядом в `docs/EKSPERIMENTY_PROGNOZ.md`).
Прогоны `enlilList` поздних карточек CME в расчёт НЕ входят ни в одном
режиме: время размещения конкретной версии карточки на сайте не доказано
(R10, принято по возражению А); прогноз Kp NOAA (3-day forecast
из выпуска до отсечки) с максимумом в окне ≥ 7 (R9) — помечен словом
«прогноз», карточка `external_forecast`. Вспышки и сами выбросы остаются
информацией в картине (по эксперименту на контрольной неделе «любое
событие → условие» давало 113 ложных пометок, раздел 10). Связанные записи
одного события — уведомление, карточки по приборам, несколько уведомлений
о приходе одного выброса (разрыв начал до 12 ч) — сводятся в одно условие с
перечнем идентификаторов записей (Т3); идентификаторы и ссылки на
первоисточник печатаются в карточке условия. Если конец события
неизвестен, для пересечения принимаются сутки от начала. Из индексов NOAA
не следует ни прерывание, ни продолжение ВКД; исключение помеченных окон —
консервативная политика прототипа, не норма (CONTRACT, раздел 4, п. 2).
Уровень S для отметки на графике — по порогам NOAA
10/100/1000/10 000/100 000 pfu (`app/norms.py`).

Прогнозы NOAA в исторических режимах (`vkd/integration/noaa_forecast.py`
→ `vkd/history/replay.py`, A2). Три канала из реестра A1: планетарный Kp
по 3-часовым интервалам и суточная вероятность S1+ (3-day forecast NOAA
NCEI), суточная вероятность протонного события (daypre). Берётся последний
допустимый выпуск с временем `Issued` не позже отсечки (в разборе — не
позже начала периода); ячейки сохраняют исходное разрешение — суточная
вероятность не пересчитывается в вероятность за окно, и это подписано;
покрытие окна объединением ячеек объявляется (полное только без пропусков;
перекрытия и дубликаты не добавляют охвата);
отсутствие выпуска (разрыв каталога 3-day forecast 15.05–16.06.2024) даёт
статус «нет допустимого выпуска» и оценку не блокирует. Текст выбранного
бюллетеня попадает в сырые записи выгрузки.

GOES как наблюдение и покрытие канала. В текущем режиме последнее
наблюдение ≥10 МэВ имеет ограниченный срок применимости (60 мин по
умолчанию), который не заполняет всё будущее окно. В «Историческом разборе»
используются 5-минутные ячейки NASA iSWA: максимальный поток и покрытие
считаются отдельно для каждого окна. В «Прогнозе из прошлого» этот архив
исключён, поскольку публикация именно этих версий к отсечке не доказана;
датированные уведомления DONKI дают только частичный охват. Отсутствие
уведомлений не доказывает нулевой поток. GOES — индикатор на геостационарной
орбите, не поток у станции. Канал >100 МэВ не подставляется в шкалу S для ≥10 МэВ.

Kp как наблюдение. Если наблюдения планетарного индекса нет (источник
исключён пользователем или публикации до отсечки нет), покрытие механизма космической погоды объявляется
частичным, а причина называется строкой «Kp: наблюдения нет». Прогноз Kp
наблюдение не заменяет: неизвестное не становится нулём и не улучшает
вердикт (версия алгоритма 0.8.0).

Покрытие и правило рекомендации (`recommend`, реализация 0.8.0).
Полнота временного интеграла требует покрытия всего окна; доля известных
точек не заменяет долю времени. Механизм сохраняет ограничения своих каналов.

1. Охват: **отсутствующее** покрытие обязательной линии хотя бы у одного
   сравниваемого окна → `insufficient`, с перечислением причин и с указанием, у
   какого окна линия пуста. **Частичное** покрытие рекомендацию не отменяет: с
   версии `0.8.0` оно объявляется строкой «Область вывода» под вердиктом — по
   каким факторам сделан вывод, на какой доле окна работала модель, какие минуты
   и почему в неё не вошли и чего вывод НЕ означает (`vkd/assess/coverage.py`,
   `tests/test_declared_scope.py`). Раньше здесь стояло «отсутствующее или
   частичное → `insufficient`» — это описание версии `0.7.0` и больше не верно.
2. Условия: помеченные окна исключаются из автоматического выбора; при полном
   охвате отсутствие кандидатов даёт `all_need_check`, один кандидат — `preferred`.
3. Космопогода сравнивается одновременно по минутам в аномалии и флюенсу:
   лучшее окно не хуже по обеим величинам и лучше хотя бы по одной с учётом
   допусков. Противоречие величин даёт `trade_off`.
4. Метеороидный фон сравнивается отдельно. Порог различимости (по умолчанию
   5 %) — настройка команды, не норма ECSS. Противоречие механизмов вне
   допусков даёт `trade_off`, без победителя.
5. Различия обеих величин в пределах допусков дают `equivalent`; допуски
   публикуются вместе с основанием и анализом чувствительности.

Отсечка по времени публикации (`vkd/assess/cutoff.py`; CONTRACT, раздел 10
и R4). В режиме «Прогноз из прошлого» каждая использованная запись
проверяется отдельно: время публикации неизвестно → исключена как
непригодная для строгого воспроизведения; опубликована после отсечки →
исключена; наблюдение с моментом позже отсечки внутри записи, опубликованной
раньше (вложенные `allKpIndex`), → исключено; своевременный внешний прогноз
на будущее — разрешён (R6). Список исключённых записей с причинами
показывается в блоке «Данные» (профессиональный уровень) и сохраняется в
снимке и в `manifest.json`. Датированные выпуски для строгого режима —
уведомления DONKI `sentNotifications` с `messageIssueTime` (берётся
более позднее из времени API и времени из реестра A1, где хранится
секундное время тела сообщения: у `20240516-7D-001` разница 13 ч 56 мин);
карточки SEP имеют только `submissionTime` (подача версии, `versionId`) и в
строгий режим не входят; прогоны `enlilList` в расчёт не входят вовсе (R10);
выпуски NOAA — с `Issued` из заголовка. Наблюдения Kp в истории поставщик
берёт из архива GFZ за 2024 (`data/gfz_2024`, A1): у интервалов
окончательного ряда нет собственного времени публикации, поэтому в строгом
режиме они исключаются с указанной причиной, а в разборе после факта
используются. В строгом режиме наблюдённый Kp всё же есть — из тела
опубликованного уведомления DONKI о буре, где он назван вместе с временем
интервала (на отсечке 10.05.2024 19:00 это Kp 7,67, уведомление
`20240510-AL-013`, выпуск 18:44Z). Численные наблюдения GOES ≥10 МэВ за
2024 берутся из архива NASA iSWA (`data/goes_2024`, 5-минутные средние):
в «Историческом разборе» это наблюдение канала, в строгом режиме архив
исключён целиком — историческая публикация и доступность именно этой
версии не доказаны, и канал остаётся покрытым датированными уведомлениями. Kp карточек DONKI: `observedTime` — конец трёхчасового
интервала (сверено с рядом GFZ за 10.05.2024).

## 8. Формат выгрузки и воспроизведение

Вкладка «Данные», две кнопки выгрузки. Экран и обе выгрузки строятся из

(CONTRACT, правило 10).

JSON (`vkd_risk_<время>.json`) — полный снимок: версия схемы и алгоритма,
время расчёта, режим, запрос (включая сдвиги окон, пороги, состояния
источников, сценарий), метаданные траектории (источник, метод, система

в текущем режиме), окна с механизмами и величинами, рекомендация,
карточки, источники со статусами (в истории — и линии прогнозов NOAA),

записи, использованные события), устойчивость (сетка, разброс,

Воспроизведение (`scripts/replay_example.py`):

```
python scripts/replay_example.py examples/gannon_2024-05-10_cutoff19Z.zip
python scripts/replay_example.py examples/gannon_2024-05-10_cutoff19Z.json
```

Скрипт читает запрос, рекомендацию, манифест и метаданные траектории из
архива (или весь снимок из JSON), запускает тот же `run()` и сравнивает
вердикт, предпочтительное окно, сравнение по механизмам, причины и условия
по окнам; печатает сохранённую и текущую версии алгоритма и сверяет коммит
кода из манифеста с HEAD. Коды возврата: 0 — воспроизведено, 1 —
расхождение, 2 — повтор невозможен, 3 — воспроизведено другой версией кода.
Для исторических режимов совпадение обязательно: входы — архив
и реестр в репозитории, орбита из OEM, отсечка; TLE не нужен, и повтор по
JSON даёт то же, что по ZIP. Для текущего
режима сохранённый TLE записывается во временный файл
`data/cache/replay_iss.tle` и передаётся через `tle_override_path`, но
совпадение не гарантируется — живые данные изменились, скрипт печатает обе
версии; JSON-снимок текущего режима не несёт сырых записей GOES/Kp/TLE и
даёт код 2 («повтор невозможен, нужен ZIP») — это задумано, а не отказ.
Проверено 19.09.2026 на коммите `7438306` (слияние восьмого круга и области
данных, версия алгоритма `0.8.0`), Windows 11 / Python 3.14.6: оба примера выше —
`gannon_2024-05-10_cutoff19Z.zip` и `…cutoff19Z.json` — дают
«РЕЗУЛЬТАТ: ВОСПРОИЗВЕДЕНО» и код 0; `python scripts/replay_all.py` даёт
**10/10 «ВОСПРОИЗВЕДЕНО», код 0** по ZIP, а по JSON — 7/7 исторических
с кодом 0 и 3/3 примера текущего режима с кодом 2 по причине выше. Код 0
требует, чтобы коммит манифеста и HEAD не различались НИ ОДНИМ файлом в
`app`, `vkd`, `experiments`, `config`, `data`, `scripts`, поэтому примеры
пересобираются последним шагом круга: любая последующая правка кода честно
переводит их в код 3 («результат совпал, версия кода другая»). Тесты
`tests/test_replay.py` и `tests/test_integration.py` закрепляют
детерминированность исторического расчёта без сети и независимость
разброса устойчивости от сохранённого допуска.

Сохранённые примеры (`examples/`, индекс `examples/INDEX.md`, созданы
`scripts/make_examples.py` 19.09.2026 в 09:30 UTC тем же конвейером, версия
алгоритма `0.8.0`, коммит кода `7438306`; исторические — на орбите OEM).
Столбец «вердикт» переписан с самих снимков после пересборки, числа взяты из
`recommendation.rule` и `robustness`, а не из памяти:

буре 27 / 0 / 18 против 18 / 9 / 10 у базовой линии, по протонному событию
17 / 19 / 0. На контроле: система по буре 1 / 4 / 14, по протонному событию
20 / 64 / 0; все 14 ложных тревог по буре на контроле приходятся на 13 и
14 мая (10 и 4 окна соответственно) — хвост той же бури Гэннон. Первая
отсечка, поставившая условие по буре на окно, в котором буря действительно
случилась: `cme_arrival` — отсечка 09.05 18:00Z на окно 10.05 12:00Z (факт:
Kp ≥ 7 с 10.05 15:00Z, то есть 21 ч между отсечкой и началом бури), прогноз
NOAA — отсечка 10.05 06:00Z на окно 11.05 00:00Z. Опубликованный прогноз
прихода выброса сработал на 12 ч раньше регулярного бюллетеня.

Линия `notif_gst` даёт нули не по ошибке: уведомление о буре сообщает
НАБЛЮДЁННЫЙ Kp за прошедший 3-часовой интервал, конец которого объявлен,
поэтому конвенция 24 ч к нему не применяется и на будущее окно оно не
распространяется. Заблаговременность дают прогнозные линии, а свежее
наблюдение Kp входит в расчёт отдельным фактором, не событием.

Чувствительность — теперь к тому, какая граница ОПУБЛИКОВАННОГО в
уведомлении диапазона максимума Kp сравнивается с порогом. У ВЕРДИКТА
СИСТЕМЫ (`system_storm`): `max` даёт 27 / 0 / 18 на событии и 1 / 4 / 14 на
контроле, `min` — 20 / 7 / 8 и 0 / 5 / 0; ложных тревог на событии при `min`
не исчезает — их 8. Отдельно взятая линия прихода выброса (`cme_arrival`)
при `min` даёт 19 / 8 / 0 и 0 / 5 / 0: ноль ложных тревог — это показатель
ОДНОЙ линии, а не поведение системы, и раньше он стоял здесь как системный
(исправлено 19.09; числа — `examples/experiments/forecast_lines.json`, ключ
`sensitivity`). Принято `[history].cme_kp_range_bound = "max"`: пропустить бурю
дороже, чем проверить окно лишний раз. Это ценностное решение, а не подбор
параметра модели — обе границы объявлены источником, и числа обеих
опубликованы рядом. Границы названы в отчёте: одно выраженное событие за
период — разбор случая, не оценка вероятностей; показатели по протонному
событию с прежней редакцией не сравнимы, потому что факт сменился с карточки
SEP по конвенции 24 ч на измеренный поток GOES.

## 12. Чего не заявляем

Дословно `CONTRACT.md`, раздел 9:

- допустимость реального выхода;
- вероятность разгерметизации и вероятность попадания в космонавта;
- дозу человека как обязательный результат;
- поток GOES как поток у станции без обрезания и без предположения о спектре;
- что учтены все внешние угрозы;
- что собственный расчёт предсказывает развитие протонного события: он
  предсказывает пересечение пространственной модели.

`policy_note` из снимка расчёта (`app/compute.py`, `POLICY_NOTE`):
«Правило команды, не норма: окно с протонным событием, бурей Kp ≥ 7
(наблюдение или прогноз) или сообщением о сближении автоматически не
выбирается — его проверяет аналитик. Шкалы NOAA сами по себе не запрещают и
не разрешают ВКД.»

Дополнительно по метеороидам (CONTRACT R7): ECSS оценивает природные
метеороиды на одну опорную пластину; вероятность повреждения скафандра и
попадания в космонавта из числа попаданий не выводится; техногенный мусор —
вне охвата; метеорные потоки конкретной даты показываются как признак
активности по календарю IMO, но их вклад в число попаданий не рассчитан.

## 13. Ограничения текущей версии

- Слои источников и истории. `app/compute.py` импортирует `vkd.sources`
  (живые источники, A4) и `vkd.history` (`history_bundle` — содержательный
  разбор DONKI, A2); после третьего круга оба импорта проходят, и действующий
  слой печатается в таблице источников строкой `_layers`. Запасные
  `experiments/legacy/stub_sources.py` и `experiments/legacy/stub_history.py` остаются в
  репозитории и включаются только при `ImportError` — то есть при работе без
  пакетов области А. Орбита — модуль А без заглушки.
- Архив наблюдений GOES за 2024 год (`data/goes_2024`, NASA iSWA,
  5-минутные средние) подключён: в «Историческом разборе» канал GOES —
  численное наблюдение с записью и охватом горизонта, ряд рисуется на ленте
  окна и выгружается файлом `observations.json`. В «Прогнозе из прошлого»
  архив исключён целиком: историческая публикация и доступность именно этой
  версии не доказаны, и канал там остаётся покрытым только датированными
  уведомлениями DONKI — это ограничение названо на экране и в снимке.
  **Чего не хватает:** датированного источника наблюдений GOES 2024
  (бюллетени SWPC с временем выпуска либо квитанция доступности версии
  iSWA); без него линия по протонному событию в строгом режиме держится
  только на пороговых уведомлениях. Kp в разборе берётся из архива GFZ
  (`data/gfz_2024`): у интервалов окончательного ряда нет собственного
  времени публикации, поэтому в строгом режиме они исключаются, а
  наблюдённый Kp там приходит из тела опубликованного уведомления DONKI о
  буре. Класс условия и срок действия из тела уведомления не
  восстанавливаются — конец без объявления принимается за 24 ч.
- Орбита в истории — объявленная реконструкция по OEM NASA/JSC (Р-О1):
  публичная доступность версии OEM в 2024 году не доказана, строгий отбор
  не проходит; выбор между реконструкцией и отказом без орбиты ждёт ответа
  А. Снимок TLE в репозитории стареет: текущий режим без сети и без свежего
  кеша через 3 сут после эпохи даёт «орбита недоступна».
- Магнитные координаты для таблиц ОСТ — эксцентричный диполь (R11),
  объявленное приближение до трассировки силовых линий (A3); используется
  только таблица минимума солнечной активности; коэффициенты диполя — на
  дату средней точки трассы. В сохранённых примерах точек без модели нет
  (`n_outside_model` = 0), но 16–39 точек на трассу имеют B/B_0 < 1 и помечены
  `inconsistent_BB0`. Отдельно от этого: внутри аномалии таблица ОСТ не даёт
  значения у 0…5 точек окна из 3…107 (точки выше точки отражения, поток там
  физически нулевой), а 14…24 % точек трассы лежат вне сетки таблиц вовсе —
  это участки сильного поля за пределами аномалии, вклада они не дают. Все три
  числа — разные величины, и на экране они стоят рядом в карточке флюенса.
- «Минут доступности частиц канала» (CONTRACT, раздел 3) теперь выдаётся:
  две величины по вертикальной жёсткости обрезания A3 (протоны ≥10 и
  ≥100 МэВ). Это порог по жёсткости без формы спектра, обрезание
  центрального диполя дано для спокойных условий, снижение обрезания при
  буре не моделируется, перенос потока GOES на станцию по-прежнему не
  делается. `CONTRACT.md` §12, R12, п. 2 приведён к коду 19.09 поправкой,
  помеченной датой.
- Прогнозы NOAA в истории покрывают не весь период: выпусков 3-day forecast
  нет за 15.05–16.06.2024 и до 1 мая; канал объявляется отсутствующим.
- Вклад метеорных потоков конкретной даты (ECSS 10.2.2.2c) в число попаданий
  не рассчитан: в число попаданий входит только спорадический фон Grün, а
  потоки даты показаны отдельной величиной-признаком по календарю IMO (ZHR —
  визуальная величина, не поток на пластину; даты календаря смещаются на
  ±1 сут по годам). Техногенный мусор не моделируется; модель изотропна.
- Текст условия по моделируемому событию сценария называет запись
  «1 запись DONKI — sim_sep#…» (`compare.py`, `rec_txt`): синтетика помечена
  словом «МОДЕЛИРУЕМОЕ», но слово «DONKI» в подписи лишнее.
- Ключ `[sources].cache_ttl_s` читает слой A4 (`vkd/sources/live.py`,
  `_configured`) — как нижнюю границу интервала запросов к источнику. Срок
  кеша ответов Streamlit к нему не привязан: он задан числом `ttl=300` в
  `app/main.py`. Значение из файла попадает в `effective_config` снимка
  (раздел 14).
- Пункты раздела 12 CONTRACT: Р-О1, Р-О2, R9 и R12 подтверждены А 19.09 в
  ограниченном смысле («объявленный метод и объявленное ограничение», не
  закрытие обещанной функции). R10 и R11 переписаны по его возражениям и
  помечены «принято А 19.09»: публикацией прогноза прихода выброса признаётся
  только опубликованное уведомление DONKI, а прогон `enlilList` по
  `modelCompletionTime` — реконструкция после факта; в `magcoords.py` нужен
  переход WGS84 (lat, lon, h) → ECEF и раздельная подпись методов для
  `cutoff_GV`. **Оба решения реализованы** на стыке третьего круга:
  условие по приходу выброса строится из структурированных `facts`
  опубликованного уведомления (`kp_range_min/max`, граница — настройка
  `[history].cme_kp_range_bound`), линия `enlilList` снята во всех режимах;
  `vkd/assess/magcoords.py` переводит WGS84 (lat, lon, h) → ECEF точно
  (`geodetic_to_ecef_km`, NIMA TR8350.2), а жёсткость обрезания осталась от
  центрального наклонённого диполя A3 и подписана отдельным полем
  `trajectory_meta.belt_coordinates.cutoff_GV_method` — за одну модель
  две разные не выдаются.
- Линия сближений SOCRATES не подключена; автоматического перебора окон и
  валидации запроса сверх границ ползунков нет.

## 14. Настройки вне кода

`config/settings.toml` (`vkd/config.py`; путь переопределяется переменной
окружения `VKD_SETTINGS`; файла нет — умолчания кода, файл сломан — ошибка,
не тихие умолчания). Секции: `[thresholds]` — все поля `Thresholds`
(`Thresholds.from_settings()`; неизвестный ключ — ошибка при запуске, не
умолчание, тест `tests/test_config.py`); `[sources]` — `timeout_s` = 6,
`total_deadline_s` = 12 и адреса `[sources.urls]` (GOES, Kp, трёхсуточный
бюллетень NOAA, цепочка из трёх адресов TLE); `[history]` — `cme_kp_range_bound = "max"` (какая граница
объявленного в уведомлении диапазона максимума Kp сравнивается с порогом),
`sep_valid_hours = 24` и `event_valid_hours = 24` (переносятся в
`Thresholds` и печатаются в тексте условия как ПОЛИТИКА, а не как
длительность события); `[ui]` — длительность, период поиска, сдвиги
