# A1/A2: архивные данные и адаптер типов 2.2

## Вход для приложения

```python
from datetime import datetime, timezone
from vkd.types import Request
from vkd.history import history_snapshot, history_bundle

t0 = datetime(2024, 5, 10, 19, tzinfo=timezone.utc)
request = Request("history_forecast", t0, 480, 1440, t0)
data = history_snapshot(request)
# data["samples"]: EnvironmentSample; data["events"]: EventInterval
# data["source_versions"][source_id][raw_record_id]: метаданные/хеш/версия
# data["coverage_map"]: покрытие каждого канала, пропуски и ограничения
# data["raw_records"]: точные исходные байты в content_base64

# Совместимость с существующим тройным результатом B1:
samples, events, raw = history_bundle(request)
proof = raw["_history"]
```

`history_bundle()` без аргументов совместим с текущим B1: возвращает
проверенный каталог исходных уведомлений DONKI вместо чтения поздних
карточек событий, а с адаптера v4 — также окончательный Kp GFZ за май–июнь.
GFZ имеет `published_utc=None` и предназначен только для разбора.
Его собственный `apply_cutoff` может отфильтровать эти
независимо датированные записи. В ветке Б с `2d20793` NOAA уже подключён через `vkd.integration.noaa_forecast`
с явной отсечкой. Для получения NOAA именно через этот bundle нужно передать
Request: без отсечки нельзя выбрать правильную версию прогноза. Для нового
потребителя предпочтителен `history_snapshot`, чтобы не потерять coverage
и source_versions при фильтрации raw только по событиям.

Ошибки формата Request — `ValueError`. Отсутствующий/повреждённый реестр —
`HistoryDataError`. Порча отдельной записи после открытия реестра даёт
явный invalid/исключение записи в отчёте, никогда не успешный пустой охват.
Все вызовы работают офлайн. Отключение сетевого источника не стирает
пригодный проверенный архив; это отмечено как `verified_offline_cache`.

Горизонт — длительность + период поиска, до 32 ч; `work_delay_min` (0–180)
сдвигает начало/конец расчётного горизонта, но не отсечку публикации.
В `history_review` наблюдения допускают поздние публикации, а панель NOAA
показывает прогноз, известный к исходному началу запроса. В `history_forecast`
публикация **и** заявленная доступность каждой записи не позже cutoff.
В review cutoff должен быть None; в forecast обязателен и не позже начала.

Наблюдательный контекст по умолчанию — 48 ч до начала. Это фильтр выборки
для экрана, **не** доказанная длительность события. Для CME учитывается
пересечение диапазона неопределённости прихода, но ±7 ч не записывается
как продолжительность бури или Valid From/To.

## Семантика DONKI

Источник формата: [NASA CCMC, DONKI API](https://ccmc.gsfc.nasa.gov/tools/DONKI/).
Разбирается `messageBody` самостоятельного уведомления из проверенного
архива, а не современная связанная карточка. Никакого дополнения из её
`allKpIndex`, времени максимума или поздних правок нет. Основная сводка
отделена от Notes; связанные события из примечаний не подменяют основное.

- GST: фактический Kp и указанный трёхчасовой интервал; timestamp численного
  наблюдения — конец интервала. Наблюдение не переносится в будущие окна.
- SEP: только явно указанные GOES в основном абзаце дают земное событие.
  `>10 MeV, >10 pfu` и `>100 MeV, >1 pfu` — разные каналы. Это нижние
  границы, не равные им измеренные значения и не готовый уровень S.
  Числовая серия GOES этим не заполняется. SOHO/STEREO исключены из линии
  GOES; ассоциированные GOES в Notes не меняют место первичного наблюдения.
- CME: только явный прогноз прихода к Земле; время старта CME у Солнца
  не становится временем прихода. Обычное упоминание Earth в названии
  системы координат не устанавливает воздействие на Землю.
  В адаптере v2 тип события `CME_ARRIVAL` совпадает с интегратором Б.
  Если тот же абзац содержит диапазон максимума Kp, сохраняются
  `facts.kp_range_min/max` и `kp_basis='published_notification_range'`.
  В note диапазон подписан явно: верхняя граница не является `kp_90`.
  Поля модели из поздних карточек `enlilList` к уведомлению не добавляются.
- FLR, IPS у L1, модельный MPC около GEO и RBE внешнего пояса — информация
  с конкретной областью применимости; не автоматические условия ВКД.
- Конец события и срок действия сообщения неизвестны → `None`, а не
  24 часа. Поля физического интервала и действия сообщения раздельны.
- Каждый выпуск сохранён отдельно. Автоматическое и ручное уведомления
  об одном событии не означают два физических воздействия; численное
  покрытие Kp считается по объединению интервалов, а не числу сообщений.
- Недельные отчёты не становятся событиями/прогнозами. API и время внутри
  сообщения сверяются до секунд. Разница от минуты помечается конфликтом;
  пример 16 мая с расхождением почти 14 ч исключён.
- Разные версии одного messageID, доступные к отсечке, исключаются как
  неоднозначные. Поздняя версия не вытесняет допустимую раннюю.

Контентная проверка фиксируется в `source_versions[*][*].content_audit`.
Структурированные факты канала/порога и неопределённости времени доступны
в `.content_audit.facts`; потребителю не нужно разбирать русский `event.note`.
Оригинальный реестр A1 остаётся неизменным. Как и у NOAA, допуск основан
на датированном выпуске провайдера; независимая историческая неизменность
полного тела не доказана. Это ограничение сохраняется в каждом снимке.
247 сообщений классифицированы: 166 разобраны, 71 относится к другим
целям/каналам, 9 недельных обзоров, 1 конфликт публикации.

## Неполнота не означает нулевой риск

`coverage_map` отдельно хранит прогнозные интервалы NOAA, редкие наблюдения
Kp, численные наблюдения GOES в разборе и инвентаризацию уведомлений.
Адаптер `history-a2-v3` подключает [архив NASA iSWA](../../data/goes_2024/README.md)
за 29.04–02.07.2024: ≥10 МэВ в pfu, исходные пятиминутные интервалы,
пробелы без интерполяции, `quality=unknown`. В строгом прогнозе этот архив
исключается: историческая публикация и доступность версии не доказаны.
Для численного GOES, как и NOAA, нужен явный Request. Сам по себе полный
временной охват не подтверждает качество прибора и достаточность рекомендации.
Пустая выборка DONKI **не** означает «событий не объявлено за весь период»
или «SEP отсутствует»: `complete_event_catalog=False`, физическая доля
покрытия неизвестна. Краткие пороговые уведомления не подменяют мониторинг.

Оригинальные channel_id сохранены: `noaa_kp` — прогноз планетарного Kp,
`kp` — наблюдение в DONKI, `mid_latitude_k`/`high_latitude_k` — другие
индексы daypre. `s1_or_greater_probability` и `whole_disk_proton_probability`
не объединяются без отдельного обоснования. Суточные вероятности остаются
суточными и не создают EventInterval о наступившем событии.

## Низкоуровневый выбор NOAA

`SourceRegistry` читает локальный реестр A1 и проверяет SHA-256, размеры,
идентификаторы, времена и единицы. При чтении raw-файла хеш проверяется
повторно. Метаданные возвращаются копиями: изменение результата в одной
сессии не меняет другие.

`replay_forecast` выбирает последний допустимый выпуск конкретного источника
и канала, разбирает исходную таблицу и возвращает значения с интервалами,
происхождением, покрытием и явными пробелами. Сетевых запросов нет.

```python
from datetime import datetime, timedelta, timezone
from pathlib import Path
from vkd.sources.registry import SourceRegistry
from vkd.history.replay import replay_forecast

registry = SourceRegistry(Path.cwd())  # запуск из корня репозитория
cutoff = datetime(2024, 5, 20, 12, tzinfo=timezone.utc)
result = replay_forecast(
    registry,
    source_id="noaa_ngdc_daypre",
    channel_id="whole_disk_proton_probability",
    cutoff_utc=cutoff,
    valid_from_utc=cutoff,
    valid_to_utc=cutoff + timedelta(hours=32),
)
assert result["record"]["release_id"] == "20240519daypre"
assert result["status"] == "full"
assert result["coverage_fraction"] == 1.0
```

В этом примере вероятность в суточных ячейках — 10%, единица `%`.
Она **не** преобразуется в вероятность за 6 или 32 часа. `cells` сохраняет
оригинальные суточные/трёхчасовые интервалы, даже если запрошено их подмножество.
`covered_seconds` и `gaps` относятся именно к запрошенному интервалу.

Статусы результата: `full`, `partial`, `missing`, `ambiguous`, `invalid`.
Это статусы данных, не оценка риска и не рекомендация по ВКД. При отсутствии
или порче данных значений нет; покрытие не выдаётся за нулевой риск.

Оба времени `published_utc` и `available_utc` должны быть известны и не позже
отсечки. Нынешняя политика допускает `dated_official_bulletin` — датированный
официальный выпуск с заявленным временем. Независимая неизменность его байтов
с 2024 года этим не доказывается, что сохраняется в ограничениях результата.
NASA OEM с неизвестной публикацией и сообщения DONKI исключены из этого
численного NOAA API; DONKI проходит отдельный содержательный разбор выше.
Неоднозначные разные байты с одной датой публикации не выбираются произвольно.

Будущие прогнозные интервалы своевременного выпуска сохраняются. Проза об
наблюдениях не превращается в прогнозные значения. Daypre Mid/High k не
подставляется в канал планетарного Kp. Имена файлов не заменяют `Issued`.

## Проверка и границы текущего результата

Из корня репозитория, без новых зависимостей:

```sh
python -m unittest discover -s tests -t . -v
```

Первоначальные 25 тестов: 390 архивных записей, разбор 6561 ячейки всех 117 выпусков NOAA,
шесть контрольных отсечек и дополнительная дата, численная проверка пробела,
поздние выпуски/редакции, конфликт версий, порча файлов, единицы, UTC и
изоляция метаданных. Тесты также обнаруживаются pytest после установки
окружения B1.

Адаптер добавляет 22 теста: тексты исходных DONKI, земная относимость,
каналы протонов, исходные интервалы, будущие наблюдения, секундная отсечка,
неоднозначные версии, порча, реестр каждого факта, изоляция снимков и
совместимость B1. Команда общей проверки — `python -m pytest -q`;
фактический результат сохранён в `data/source_registry_2024/a2/verification.json`.

Контрольные даты и пример полного JSON — `data/source_registry_2024/a2/`.
Интеграция A2/A3/A4 реализована в накопительной ветке Codex 0.6.x:
приложение передаёт Request, использует численный GOES в разборе, сохраняет
coverage/source_versions и точные байты в ZIP. Replay приложения на 0.6.0
проверен на 9/9 примерах; после каждого следующего объединения требуется
повторная проверка на новом SHA. Детали —
`docs/integration/INTEGRATION_CLOSEOUT_2026-09-19.md` и свежий журнал А.

Время измерения GOES iSWA **не является доказанной исторической публикацией**.
Timestamp-proof фиксирует как раз отсутствие такого доказательства: данные
допустимы для разбора, но не как наблюдения строгого прогноза на 10.05 19:00.
Датированные уведомления DONKI остаются отдельным допустимым источником;
их пороговое сообщение не заменяет численное измерение GOES.


## GFZ Kp, адаптер v4

`data/gfz_2024/` сохраняет точный байтовый срез исходного файла коллеги:
61 сутки, 488 трёхчасовых ячеек. Реестр проверяет SHA-256 и длину;
парсер проверяет заголовок, даты, диапазон и округлённые трети Kp, D-флаг.
Пропуск `-1.000` создаёт пробел, ошибочные значения дают отказ.
Время наблюдения — конец интервала; D=1/2 означает окончательный Kp.
Неизвестная историческая публикация исключает GFZ из строгого режима.

В `history_snapshot(request)` покрытие GFZ и суммарное покрытие наблюдений
Kp считаются по пересечению фактических ячеек с горизонтом, с учётом задержки.
48 часов контекста не входят в знаменатель покрытия окна. Последнее
наблюдение не продолжается за правый край архива. DONKI сохраняется отдельно:
его датированное наблюдение может пройти строгую отсечку, окончательный GFZ — нет.
При одинаковом времени legacy-потребитель `max(..., key=t_utc)` получает
GFZ первым; оба факта остаются прослеживаемыми, их нельзя складывать/усреднять.

Проверка 24 значений и времён против отдельно полученного официального JSON
GFZ сохранена в `data/gfz_2024/validation/`. Это сверка форматов одного
поставщика, не независимая физическая валидация Kp.
