## Серьёзные

**R4-1. Ползунки сдвига окон обнуляются при любом движении периода поиска** (`app/main.py`).
**ЗАКРЫТО четвёртым кругом.** Состояние на `9614128` было такое (оставлено для разбора): пересчёт сдвигов
ДО создания ползунков в коде есть (`app/main.py`, строки 112–139: `spread_offsets`, подпись
«сдвиги пересчитаны под период»), совпавшие сдвиги больше не гасят экран (строки 141–150).
Невиджетных ключей `_off0/_off1/_off2` при этом нет — сохраняется только `_search_prev`,
поэтому обещанную проверку ниже прогнать обязательно, прежде чем считать пункт закрытым.

Исходное описание (19.09, утро). Падения экрана больше нет (U1 закрыт наполовину), но при смене «Периода поиска начала» меняется
`max_value` виджетов сдвига, Streamlit теряет их сохранённые значения и оба сдвига уходят в 0.
Пользователь, двигая один ползунок, теряет настройку окон. Исправление: хранить сдвиги в
невиджетном ключе состояния (`_off0`, `_off1`, `_off2`), каждый прогон читать оттуда, ограничивать
диапазоном `[0, search_min]` и разводить при совпадении; виджетам отдавать значение из этого ключа.
Проверка: AppTest — задать сдвиги 120/360, сменить период 1440 → 720 → 360, сдвиги сохраняются
(с ограничением по новому периоду), вердикт на месте.

**R4-2. ЗАКРЫТО четвёртым кругом. Предупреждение о границе архива не совпадает с признаком покрытия** (`app/main.py`,
`app/compute.py`). Состояние на `9614128` (оставлено для разбора): `app/main.py:231-232` — `horizon_min = search_min + duration_min`
и условие `t0 + horizon_min > ARCHIVE_TO`, про `max(offsets)` в нём ничего не было.

Исходное описание (19.09, утро). Предупреждение включается по `t0 + search_min + duration_min > ARCHIVE_TO`,
а покрытие считается по фактическим окнам. Если сдвиги меньше периода поиска, сверху написано
«рекомендации не будет», а вердикт даёт предпочтительное окно — противоречие на одном экране.
Исправление: условие предупреждения свести к тому же признаку, что и покрытие:
`t0 + max(offsets) + duration_min > ARCHIVE_TO`. Сделано (`app/main.py`, строки 242–243).

**Рецепт приёмки исправлен пятым кругом (19.09, прогон AppTest на `925f923`).** Прежний рецепт
из этого пункта — «30.06.2024 20:00 со сдвигами 0/120: предупреждения нет, вердикт есть» —
**невыполним**: при длительности по умолчанию 360 мин последнее окно кончается 01.07 04:00,
то есть за границей архива (`ARCHIVE_TO` = 01.07.2024 00:00), и предупреждение появляется
законно. Прогон это и показал: предупреждение ЕСТЬ, вердикт «Оснований для рекомендации
недостаточно» — то есть код верен, а рецепт был написан под другие числа.

Действующий рецепт, «Прогноз из прошлого», дата 30.06.2024, период поиска 720 мин
(проверено тремя прогонами `AppTest`, исключений нет ни в одном):

| час | длительность | сдвиги | предупреждение о границе архива | вердикт |
|---|---|---|---|---|
| 12:00 | 60 мин | 0 / 120 | нет | «Компромисс: механизмы указывают на разные окна» |
| 12:00 | 60 мин | 0 / 720 | есть | «Оснований для рекомендации недостаточно» |
| 20:00 | 360 мин | 0 / 120 | есть | «Оснований для рекомендации недостаточно» |

Признак «годно»: предупреждение и вердикт согласованы — предупреждение появляется тогда и
только тогда, когда последнее окно выходит за `ARCHIVE_TO`, и вместе с ним приходит отказ
от рекомендации, а не предпочтительное окно.

## Мелкие, но видимые

**R4-3. ЗАКРЫТО четвёртым кругом. Отрицательная давность Kp на экране** (`app/compute.py`, `_src` и исторический блок).
Состояние на `9614128` (оставлено для разбора): `app/compute.py:549` считал `round((t0 - (kp.valid_to_utc or kp.t_utc))...)`
без `max(0, ...)`; ни одного `max(0` в файле не было.

Исходное описание (19.09, утро). `compare.py` клампит давность через `max(0, ...)`, `_src` — нет; у живого Kp GFZ текущий
3-часовой интервал ещё не закончился, и в таблице источников появляется отрицательное число.
Исправление: тот же `max(0, round(...))` в обоих местах. Проверка: тест на равенство давностей
в факторе и в таблице источников, обе неотрицательны.

**R4-4. ЗАКРЫТО четвёртым кругом. Регулярное выражение чистки источника режет содержательный текст** (`app/ui.py`,
`_RECORDS_TAIL_RE`). Состояние на `9614128` (оставлено для разбора): `app/ui.py:376` — `[;,]?\s*запис[ьи]:\s.*$`, то есть
срезался весь хвост после «записи:», включая время публикации.

Исходное описание (19.09, утро). Задумано резать перечень идентификаторов записей, но у условия по протонному
событию источник сформулирован «NASA DONKI, записи: публикация 05-09 13:54Z — 05-10 14:19Z», и на
оперативном уровне пропадает время публикации — то есть ровно то доказательство, за которое даются
баллы по О4. Исправление: сузить выражение до перечня идентификаторов (после «записи: » требовать
токен вида `[a-z][a-z0-9_]*#`), либо в `cards.py` собирать строку так, чтобы время публикации шло
до перечня. Проверка: AppTest — на оперативном уровне в карточке условия видно время публикации.

**R4-5. ЗАКРЫТО третьим кругом. Английские имена сценариев прогона в тексте карточки** (`vkd/explain/cards.py`,
`_COND_LIMITS['GST']`). Проверено 19.09: строк `kp_90`/`kp_180` в `vkd/explain/cards.py` нет —
вместе с R10 снята сама линия `enlilList`. В `app/ui.py:389` остался только словарь перевода
этих имён на русский, он срабатывает на архивных текстах и идентификаторов не печатает.

Исходное описание (19.09, утро). На оперативном уровне печаталось «оценка kp_90 (верхняя при южном
поле — kp_180)». Исправление: «оценка прогона модели при повороте межпланетного магнитного поля
на 90° (верхняя граница — при южном направлении поля)». Проверка: скан оперативного уровня
не находит `kp_90`, `kp_180`.

**R4-6. ЗАКРЫТО третьим кругом. Точка вместо запятой в самой заметной строке экрана** (`app/ui.py`, `verdict_panel`).

Исходное описание (19.09, утро). Текст правила не проходил через `frac_ru`, поэтому в панели
вердикта печаталось «разница 0.006 %» и «×1.50», тогда как ниже в списке причин — с запятой.

**R4-7. ЗАКРЫТО. Устаревшие числа эксперимента в настройках и передаче дел.**
Проверено 19.09 вечером на `9614128`. Оба места, которые пункт требовал исправить, уже не
содержат старых чисел: в `config/settings.toml` ключа `enlil_kp_fields` нет вовсе (остался
`[history].cme_kp_range_bound` с комментарием, что поля прогона WSA-ENLIL не используются),
в `docs/EKSPERIMENTY_PROGNOZ.md` строк `kp_90`/`kp_180` не осталось, а в
`docs/HANDOFF_2026-09-19.md` §10.4 числа переписаны.

Существенно: числа «69 против 6», записанные в этом пункте утром, **тоже устарели** — они
относились к снятой линии прогона `enlilList`. После перевода R10 на опубликованные уведомления
DONKI чувствительность считается по границе объявленного в уведомлении диапазона Kp
(`cme_kp_range_bound`), и по `examples/experiments/forecast_lines.json` (поле `sensitivity`)
она такая (попадания / пропуски / ложные тревоги):

| граница | линия прихода выброса `cme_arrival` | вердикт системы `system_storm` |
|---|---|---|
| `max` (наша), дни бури | 27 / 0 / 18 | 27 / 0 / 18 |
| `max`, контроль | 1 / 4 / 14 | 1 / 4 / 14 |
| `min`, дни бури | 19 / 8 / 0 | **20 / 7 / 8** |
| `min`, контроль | 0 / 5 / 0 | 0 / 5 / 0 |

**Поправка пятого круга (19.09, прочитано из файла):** прежняя запись этого пункта —
«`min` — 19 / 8 / 0» — называла только линию `cme_arrival` и выдавала её за поведение системы.
На верхней границе обе линии совпадают, на нижней — нет: у вердикта системы 8 ложных тревог,
а не ноль. В тексте всегда называть, какая из двух линий имеется в виду.
Правило остаётся прежним: числа брать из `forecast_lines.json`, а не из памяти и не из этого файла.

## Из оценки судьи, не закрытое ни вторым, ни третьим кругом

**R4-8. ОТКРЫТО (подача). Роль линии метеороидов в выборе окна.** Сервис сам печатает «окна
не различаются» с разницей в тысячные доли процента (по девяти примерам 0,0007…0,007 %). Это не дефект расчёта, а вопрос подачи: на экране и на слайде линия должна
быть заявлена как абсолютная оценка и охват, а выбор окна — за космопогодой. Проверить
формулировки в панели вердикта и в карточке.

**R4-9. ОТКРЫТО (подача). Польза дополнительных функций через сравнение** (критерий О7 требует «подтверждают
пользу примером или сравнением»). На вкладке устойчивости добавить одну строку вида: «без сетки
порогов сервис назвал бы окно N предпочтительным; на сетке выбор меняется, поэтому вердикт —
равнозначны». Данные для этой строки уже есть в `Robustness.ranking_by_grid`.
