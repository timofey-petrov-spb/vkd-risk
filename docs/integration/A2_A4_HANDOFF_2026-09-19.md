# Передача A2/A4 на базе main 73a2ec8

Ветка `codex/a4-live-sources` включает A2, A4 и оставшиеся исправления A3
из PR #1. Основная передача — эта ветка; промежуточная `codex/a2-history-adapter`
содержит A2 v1. После интеграции актуальны `history-a2-v2`, `donki-body-v2`,
`live-a4-v1`, общие типы **2.1 согласованы**. Main объединяет Б.

## Что подключается автоматически

- `vkd.history.history_bundle()` — проверенные исходные DONKI вместо карточек.
- `vkd.sources.goes_latest/kp_latest/tle_latest` — текущие источники вместо stub.
- Существующие орбитальный мост и исторический NOAA Б сохранены.
- `noaa_latest()` — готовая отдельная функция текущего прогноза; её вызов
  в live-конвейере ещё должен добавить Б. Исходные 3-часовые/суточные ячейки.
- Конфиг Б применяется к адресам, тайм-аутам и TTL A4; исходные receipt
  доступны для полноценного Manifest. Подробнее `vkd/sources/README.md`.

## Обязательные действия интегратора Б

1. **Исторический run не должен обращаться к текущим источникам.** Сейчас
   `app/compute.py` получает GOES/Kp/TLE до выбора режима, а их `live_ok` /
   `from_cache` попадают в исторический снимок. Между сетевым получением
   и кешем меняются сериализованные данные. Истории нужны её закреплённые
   источники; транспортную текущую диагностику держать вне снимка расчёта.
2. **Сохранить A2-аудит и A4-реестр.** `raw['_history']` несёт покрытие и
   source_versions, но фильтрация только по event.raw_record_id теряет этот
   объект. A4 raw имеет `{metadata, encoding, content_base64, selected}`;
   metadata → `Manifest.source_versions[source_id][raw_record_id]`. Для TLE
   сохранить `Fetch.raw/metadata` дополнительно к нормализованному staging.
3. **Использовать структурированные факты.** Для GST `facts.kp` и численный
   EnvironmentSample содержат точный индекс; regex только `Kp до …` не
   распознаёт наше `Наблюдение Kp=…`, превращая известный слабый индекс в
   «уровень не назван». Для SEP есть отдельная энергия 10/100 МэВ; пороговое
   сообщение не равно измеренному потоку или уровню S. Для CME имя уже
   согласовано с потребителем: `CME_ARRIVAL`, диапазон `facts.kp_range_min/max`.
4. **Не выдавать неизвестный конец за исходные 24 ч.** A2 сохраняет end/valid
   None и неопределённость прихода отдельно. В app и compare всё ещё есть
   `a0 + 24 h`; если сохраняется проектная политика, она должна быть отдельной
   настройкой/причиной, не длительностью события. Каталог уведомлений не
   доказывает непрерывный охват и отсутствие событий.
5. **Перезапустить Т5 на том же адаптере, что приложение.** Сейчас
   `experiments/forecast_lines.py` импортирует `experiments.stub_history`,
   приложение уже использует A2. Сохранённые показатели не характеризуют
   новую систему. Выбранное по «контролю» поле kp_90 делает этот период
   настройочным; для независимой проверки нужен другой период/разделение.

## R10: ENLIL и Kp — согласовано только с уточнением источника

Датированный прогноз прихода допустим как внешняя линия. Но
`modelCompletionTime` — завершение прогона, **не доказанная публикация
конкретной версии карточки**. API также имеет отдельные поля submission/version;
наличие сегодняшнего `enlilList` не доказывает его состав на старой отсечке.
Источник: [официальная схема DONKI](https://ccmc.gsfc.nasa.gov/tools/DONKI/).
Такие карточки можно хранить отдельно как реконструкцию до проверки доступности.

В A2 уже есть проверяемая альтернатива: время прихода и диапазон Kp из
оригинального опубликованного уведомления. На 10.05 12Z сообщения
20240508-AL-012 и 20240509-AL-010 дают предупреждение для обоих проверенных
окон; на 03.05 и 20.05 лишних условий нет. Сравнение — соседний JSON.
Верхняя граница диапазона подписана явно и **не** подставлена в поле kp_90.

Кроме того, `kp_90` означает сценарий clock angle 90°, а не автоматически
среднее, медиану или наиболее вероятный прогноз: см. [NASA CCMC, слайд 13](https://ccmc.gsfc.nasa.gov/publicData/SWxWorkshops/2014/Mays_Demo_ExtraSlides_201409.pdf).
Выбор этого сценария требует отдельного обоснования; меньшая ошибка на уже
использованном контроле не превращает его в «типичное» состояние поля.

## R11: эксцентричный диполь — статус приближения, проверка ещё открыта

Ненулевой результат сам по себе не валидирует координаты. В реализации Б
нужна точечная проверка:

- `lat_deg` A3 геодезическая, но `belt_coordinates` строит вектор сферической
  формулой. Для ECEF требуется перевод WGS84 с геодезической высотой;
  использовать исходный ECEF или корректное преобразование.
- После `replace(L=…, B_over_B0=…)` поле `cutoff_GV` остаётся от центрального
  диполя A3. Методы разных величин надо подписать раздельно; один набор
  нельзя выдавать за согласованную систему координат одной модели.
- |B| полного IGRF / B0 диполя остаётся смешанным приближением, не McIlwain L
  и не трассировкой. Пропуски/`inconsistent_BB0` не должны становиться нулями.

Р-О1 (OEM-реконструкция отдельной линией) и R9 (Kp≥7 как объявленная
политика прототипа) подтверждены в журнале. Полная научная приёмка не заявлена.
