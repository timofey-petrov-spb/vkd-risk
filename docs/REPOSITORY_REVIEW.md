# Подготовка к разработке ВКД-Риск

Проверено Codex 18.09.2026. База анализа: коммит `e6fdb54` и все 44 отслеживаемых файла. Проверены инструкции, весь Markdown, исходник C++, скрипты и конфигурация сборки, структура всех CSV/JSON и файлов космопогоды, текст приложенных источников. Для ECSS подробно проверен раздел 11, для тезисов xEMU — весь текст. Это анализ готовности проекта, а не независимая валидация всех физических моделей и действующих нормативов.

## Что предстоит разработать

Настольное приложение на C++20/Qt. Пользователь задаёт орбиту, время и длительность выхода, тип скафандра, положение светофильтров и ориентацию. Приложение должно показать дозу и ожидаемое число попаданий микрочастиц по зонам, распределение защиты и подходящее окно выхода. Вердикт допустим только при наличии проверенной модели и соответствующего предела.

| Часть | Содержание | Ответственный |
|---|---|---|
| Геометрия | Примитивы, пересечения лучей, самозатенение, распределение толщин | Claude |
| Радиация | Чтение ОСТ, интерполяция, секторная свёртка | Claude |
| Пределы | Раздельные величины дозы, пределы, обоснованный вердикт | Claude |
| Интерфейс | Лента времени, силуэт зон, гистограмма защиты | Claude |
| Орбита | TLE, распространение, координаты и высота, магнитное поле, аномалия | Codex |
| Попадания | Потоки и размеры частиц, ориентация, проекция площади зон | Codex |
| Сцена | 3D-показ скафандра и окраска результатами расчёта | Codex |

Стыки: поля зоны из `CONTRACT.md` и массив среды во времени. Общие заголовки пишет Claude. Договор правят люди. Вероятность разгерметизации не входит в согласованный результат.

Порядок реализации из `docs/ZAMYSEL.md`: геометрия → доза → пределы → орбита/окно → попадания → 3D-показ. Сегодня добавлены только инструменты подготовки и проверки окружения, без кода расчётного решения.

## Что действительно уже есть

- `src/main.cpp`: окно проверки окружения. Расчётов, реестра модулей, плагинов и интерфейсных заголовков ещё нет.
- `CMakeLists.txt` и Windows-пресеты `mono`/`dll`: оба собирают это окно. Переключение флага пока не доказывает работу загрузчика DLL или удержание регистрации модулей статическим линкером.
- 12 CSV ОСТ: каждый содержит 9 толщин и 16–18 высот. Проверены размеры строк, числовой формат, конечность и неотрицательность значений, порядок толщин. Сверка всех чисел с исходным ОСТ невозможна: оригинала нет в репозитории.
- 6 файлов космопогоды: TLE, IGRF-14, GFZ, GOES, прогноз и числа пятен. GOES содержит 6880 записей с 14 по 17 сентября; файл GFZ заканчивается 16 сентября. Это снимки данных, а не автоматическое обновление.
- Два приложенных источника: ECSS-E-ST-10-12C (106 страниц) и тезисы NASA по xEMU (DOCX).
- Инструкции обоим агентам, договор и журналы работы.

## Что нужно согласовать или исправить перед реализацией

### 1. Устаревшие документы

`docs/ARHITEKTURA.md` описывает Python, Streamlit, CadQuery и отказ от DLL. `docs/STEK_VOZDEYSTVIYA_LITERATURA.md` прямо отменяет этот вариант: актуальный продукт — C++/Qt с двумя режимами сборки. Не устанавливать старый веб-стек как обязательную зависимость продукта.

В `docs/arhitektura_geometrii.md`, раздел 6, и в старой архитектуре осталось обещание вероятности пробоя. Его перекрывают `CONTRACT.md`, раздел 9, и более новый замысел: выдаём ожидаемые попадания, не вероятность разгерметизации.

### 2. Исходные документы отсутствуют

Из 11 документов, перечисленных как имеющиеся, в Git лежат только два. Не найдены оригиналы ОСТ 134-1044-2007, ГОСТ 25645.215-85, ГОСТ Р 25645.165-2001, ГОСТ Р 25645.167-2005, ГОСТ Р 25645.166-2004, ГОСТ 25645.202-83, ECSS-E-ST-10-04C, NASA ISS EVA Suits и ERI-000501.

В частности, отсутствуют `5831.pdf` и `4293854146.pdf`, на которые ссылается план оцифровки. Также нет `data/gost165/`, `data/gost167/`, `data/zones.csv`, `data/materials.csv`, `include/vkd/`. Пределы кожи и хрусталика по исходному тексту ООКОКП-2004 в репозитории не подтверждены.

`scripts/ost_parse.py` использует вход `ost1044.txt` и выход `ost_tables` относительно текущего каталога; такого входа в Git нет. Это вспомогательный разовый скрипт, а не воспроизводимый конвейер подготовки имеющихся CSV.

### 3. Сборка и совместимость

- Версия формата `CMakePresets.json` — 6; ей нужен CMake **3.25+**, хотя README и поле минимальной версии указывают 3.21. Используем установленный более новый CMake; изменение общего файла оставлено владельцу сборки. Основание: [документация CMake](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html).
- Оба общих пресета ограничены Windows. Монолит явно запрещён без MSVC. Нативная разработка на Mac возможна с `VKD_MONOLITH=OFF`; отдельный скрипт уже проверен.
- `scripts/build_check.bat` имеет собственные жёстко заданные пути, поэтому правка только `setup_env.bat` его не настраивает. Добавлен отдельный `build_check_windows.cmd` с обнаружением Visual Studio.
- `setup_env.bat` заканчивает `setlocal`, вынося наружу только PATH/QT_DIR/OCCT_DIR. Остальные переменные MSVC, например INCLUDE и LIB, так не сохраняются. Новый проверочный скрипт настраивает MSVC и собирает в одной среде.
- `VKD_WITH_OCCT` пока только объявлен: `find_package(OpenCASCADE)` и линковки в проекте нет. Установленный Windows SDK OCCT — подготовка к дальнейшему подключению.
- `VKD_BUILD_TESTS` пока вызывает только `enable_testing()`: тестов нет. Все три конфигурации сообщают `No tests were found`. Это не зелёные физические тесты.
- Для будущих DLL нужно согласовать архитектуру x64, toolset MSVC, Qt, конфигурацию Release/Debug и CRT. Одинакового номера Qt недостаточно для гарантии бинарной совместимости.

### 4. Уточнения физической модели

- Десятилетние/усреднённые дозовые таблицы сами по себе не задают зависимость дозы от момента на орбите. До обещания конкретного безопасного времени выхода нужен согласованный способ получить среду во времени и проверить её нормировку.
- Переход дозы в кремнии к дозе в ткани нужно определить отдельно от весового коэффициента излучения. Само умножение на `w_R` этот переход не выполняет.
- ECSS-E-ST-10-12C, пункт **11.5 d**, допускает масштабирование к эквивалентной поверхностной массе только при обосновании завышения тяжести воздействия. В документах проекта консервативность Z/A пока заявлена без такого расчёта. Это вопрос валидации модели; замороженные числа договора самостоятельно не менялись.
- Таблицы весов в приложенном ECSS относятся к ICRP-60; на странице 97 сам стандарт предлагает проверять более новые рекомендации. Нельзя выдавать выбранную редакцию за автоматически проверенные действующие нормы.
- В договоре семь идентификаторов, но два относятся к альтернативным состояниям одного шлема. Площадь шлема нельзя учитывать дважды при суммировании.
- В размерной спецификации пример длины плеча неверен арифметически: `0,186 × 176 = 32,736 см`, а не 26,4 см. Перед кодированием выбрать формулу/исправить пример.
- Число 96% относится к конкретному исследованию xEMU; это мотивация зонной модели, а не универсальный коэффициент для любого скафандра. Аналогично отношение доз 12× относится к приведённому расчётному сценарию.

## Следующие действия двух разработчиков

1. Сверить версии по `docs/DEVELOPMENT_ENVIRONMENT.md` и снимкам `docs/environment/`.
2. Добавить отсутствующие оригиналы источников либо явно указать их внешнее хранение; после этого продолжать оцифровку.
3. Claude создаёт согласованные интерфейсы, подключение модулей и физические тесты. Общую сборку и договор Codex не менял.
4. Codex реализует свой контур орбиты/потоков/сцены по этим интерфейсам. Проверять интеграцию маленькими коммитами и записями в журналах.
5. После появления настоящих модулей повторить сборку и тесты обоих Windows-режимов. Текущая проверка подтверждает инструменты, но ещё не совместное написание и объединение расчётного кода.
