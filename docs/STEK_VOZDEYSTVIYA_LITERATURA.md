# 1. Стек

Приложение целиком на C++ и Qt, как SafeSatelleS. Python остаётся только
офлайн-инструментом подготовки данных и в поставку не входит.

## 1.1 Основа

| слой | что | примечание |
|---|---|---|
| язык | **C++20** | как в SafeSatelleS, `CMAKE_CXX_STANDARD 20` |
| компилятор | MSVC 2022 | обязателен: `/WHOLEARCHIVE` есть только у него |
| сборка | CMake + Ninja | пресеты в `CMakePresets.json` |
| интерфейс | **Qt 6.5+** | Core, Gui, Widgets, Charts, Concurrent |
| 3D-сцена | Qt6::OpenGL, OpenGLWidgets | либо вьюер OCCT |
| геометрия и STEP | **OpenCASCADE 7.9.2** | опционально, флагом |
| тесты | QTest | тесты на инварианты, см. п. 4 |
| установщик | **Inno Setup** | `.iss`, опыт августа переносится |
| QR на ссылку | генерируется офлайн | см. п. 1.5 |

## 1.2 Раскладка библиотек

Повторяем схему SafeSatelleS, она проверена:

```
vkd_base      Qt6::Core, Qt6::Gui                 типы, единицы, зоны
     ↓
vkd_core      + Qt6::Network, Qt6::Sql            ФИЗИКА, реестр модулей
   (vkd_sdk.dll — то, что линкуют плагины)
     ↓
vkd_widgets   + Qt6::Widgets, Qt6::Charts         общие виджеты, QPainter-визуалы
     ↓
VKDRisk.exe                                       хост, меню, загрузка модулей
```

Плагины линкуют `vkd_core` и кладутся в `modules/` рядом с приложением.

## 1.3 Два режима сборки, оба живые с первого часа

Это единственное жёсткое требование к архитектуре.

```
-DVKD_MONOLITH=ON    STATIC + /WHOLEARCHIVE   разработка, демонстрация страховки
-DVKD_MONOLITH=OFF   SHARED                   показ архитектуры, поставка
```

Разрабатываем в монолите: быстрее и модуль не может молча выпасть.
Показываем и ставим в DLL-режиме. Сломается загрузка DLL ночью — переключаем
флаг, приложение живо.

Механизм у вас уже написан, `SAFESAT_MONOLITH` в текущем `CMakeLists.txt`.

## 1.4 Плагинный ABI

Берём вашу схему целиком, она хорошо спроектирована:

- плагин — SHARED-библиотека, линкует `vkd_sdk`, экспортирует C-функции;
- `vkd_plugin_abi_version()` и `vkd_register_modules(ModuleRegistry&)`;
- резолв **по имени**, без метаданных Qt и без build-key;
- парный `vkd_destroy_module()` — кто создал, тот и удаляет;
- хост принимает диапазон версий, несовпадение отклоняет с записью в журнал;
- второй тип — UI-модуль, приносит своё окно и сам попадает в меню.

**Заголовки интерфейса пишутся в первый час и замораживаются.** Это контракт
между двумя ассистентами, и он проверяется машиной при загрузке.

## 1.5 Модули, которые делаем

| DLL | содержание | кто |
|---|---|---|
| `vkd_mod_geometry` | примитивы, трассировка, гистограмма толщин | Т |
| `vkd_mod_radiation` | таблицы ОСТ, свёртка, доза по зонам | Т |
| `vkd_mod_limits` | пределы, вердикт, запас | Т |
| `vkd_mod_orbit` | TLE, трасса, аномалия, окно | товарищ |

| `vkd_uimod_suit` | 3D-сцена скафандра, покраска по дозе | товарищ |

## 1.6 Поставка и QR

1. `cmake --build` в DLL-режиме, `windeployqt`, Inno Setup собирает `.exe`.
2. Установщик выкладывается в **GitHub Releases** — постоянная ссылка,
   бесплатно, выглядит прилично.
3. QR на эту ссылку генерируется офлайн (любой генератор или Python-скрипт
   с `qrcode`), кладётся картинкой на последний слайд.

QR ведёт на страницу релиза, а не на прямой файл: страница переживает
перезаливку и показывает версию.

## 1.7 Где остаётся Python

Только офлайн, в репозитории, в поставку не входит:

- разбор ОСТ 134-1044-2007 в CSV — **уже сделано**, `data/ost_parse.py`;
- оцифровка ГОСТ Р 25645.165 и ГОСТ Р 25645.167;
- генерация QR.

# 2. Основные воздействия

## 2.1 Нормативный перечень

ECSS-E-ST-10-12C, пункт 11.3: для пилотируемых миссий анализируются

1. захваченные протоны и электроны радиационных поясов;
2. солнечные протоны и ионы;
3. протоны и тяжёлые ядра галактических лучей;
4. тормозное излучение как вторичное от электронов;
5. вторичные протоны, нейтроны и ядерные фрагменты.

Удар микрочастиц к радиации не относится и идёт отдельным контуром.

## 2.2 Ранжирование по вкладу

Из расчёта по извлечённым таблицам и из данных NASA:

| воздействие | чем доминирует | величина |
|---|---|---|
| **электроны ЕРПЗ** | накопленная доза на кожу | около 90 % дозы в тонких зонах |
| **удар мусора и метеороидов** | мгновенный отказ оболочки | **96 % риска в мягких зонах** (NASA, xEMU) |
| **вспышка СКЛ** | острое поражение | в среднем мало, в событии решающее |
| протоны ЕРПЗ | доза на органы, проникают глубже | второй вклад по дозе |
| ГКЛ | фон | малый на низкой орбите |
| тормозное излучение | уже внутри таблиц К.1.5 | отдельно не считаем |

**Главный вывод проекта.** Оба доминирующих воздействия концентрируются
в одних и тех же зонах: руки, ноги, перчатки. По дозе рукава получают
в 12 раз больше шлема, по удару там же 96 % риска. Усреднение по скафандру
этот факт уничтожает.

## 2.3 Сценарии в приложении

ECSS-E-ST-10-12C, пункт 11.5: облучение экипажа оценивается для

1. штатной среды;
2. события солнечных частиц;
3. прохождения радиационных поясов;
4. условий, когда тридцатисуточная среда превышает штатную в пять раз.

Это готовый переключатель режимов, обоснованный стандартом.

Там же требование учитывать **самозатенение телом**, и в примечании прямо
назван случай — космонавт во время внекорабельной деятельности.

## 2.4 Что сознательно не считаем

| | почему |
|---|---|
| деградация полимеров от радиации | пороги 10⁵…10⁷ Гр против дозы 10⁻² Гр, разрыв 7 порядков |
| атомарный кислород и УФ | это ресурс скафандра, а не риск конкретного выхода |
| тепловой режим | другая система |
| **вероятность разгерметизации** | нет валидированного уравнения пробоя для ткани |

Последнее сказать на защите прямо: NASA понадобилось **более ста
высокоскоростных выстрелов**, чтобы получить уравнения пробоя для конкретного
пакета ткани xEMU. У нас таких данных нет, поэтому мы даём карту экранирования
и число попаданий, а не вероятность отказа.

## 3.2 Ключевые численные опоры

**Пределы, ГОСТ 25645.215-85:**

```
G_н(T) = 0,05 + 4·(1 − exp(−T/72))          Зв, T в месяцах
контрольная часовая = G_н(T) / (720·T)
нормативный риск = 0,6·10⁻⁴ на месяц
за профдеятельность ≤ 4 Зв,  однократно ≤ 0,5 Зв
действующий годовой 500 мЗв (СанПиН 2.6.1.44-03-2004)
```

**Функция качества, ICRP-60, через ECSS-E-ST-10-12C:**

```
L < 10 кэВ/мкм       Q = 1
10 ≤ L ≤ 100         Q = 0,32·L − 2,2
L > 100              Q = 300/√L
```

**Переход материала в алюминиевый эквивалент:** умножить на (Z/A)/0,4818.
Полиэтилен 1,184, вода 1,152, поликарбонат 1,094, тефлон 0,996.

**Зоны, Al-эквивалент:** шлем 0,722 и 1,335 со светофильтрами, торс 0,641,
рукава и ноги 0,180, перчатки около 0,22, металл «Орлана» 0,324.

**Геометрия свёртки, ОСТ 1044 приложение И:** ядром берём таблицу
**плоскости** (нормальное падение), суммируем по секторам с весом телесного
угла. При малых толщинах существен обратно рассеянный поток, стандарт
предписывает считать барьер толщиной 2R и брать дозу на глубине R.

# 4. Правила написания кода

Восемь правил. Каждое проверяется грепом или тестом.

**1. Никаких молчаливых клампов.** Значение вне области применимости — отказ
с сообщением, а не тихое приведение к границе. Это сквозной дефект, найденный
во всех трёх аудитах SafeSatelleS, и он самый дорогой: программа продолжает
считать и выдаёт правдоподобное неверное число.

**2. Единицы в имени.** `d_g_cm2`, `t_s`, `E_MeV`, `dose_mGy`. Не `d`, не `t`.
Половина ошибок на стыке двух авторов — это единицы.

**3. Ни одного `setStyleSheet` в коде.** Всё оформление в одном `.qss`,
три цвета, один шрифт. В текущем SafeSatelleS 240 вызовов при существующем
`style.qss` — отсюда вид вайбкодинга. Проверяется одной командой грепа.

**4. Каждая физическая константа с источником в комментарии.** Документ,
пункт, таблица. Число без источника в ядро не попадает.

**5. Заголовки интерфейса заморожены.** Меняются только по устной
договорённости вдвоём и с поднятием версии ABI.

**6. Кто создал в DLL, тот и удаляет.** Ваше правило, уже действует, переносим.

**7. Никаких глобальных переменных через границу DLL.** Состояние передаётся
через контекст.

**8. Тесты на инварианты, а не на значения.** Метод, который у вас уже
сработал в аудитах. Два обязательных:

- поворот всей модели в изотропном поле не меняет интегральный результат;
- секторное суммирование равномерной полусферы воспроизводит табличное
  значение полусферы из ОСТ.

Первый ловит ошибки в угловых весах, второй — в ядре свёртки.
